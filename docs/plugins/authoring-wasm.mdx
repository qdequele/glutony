title: Authoring a WASM plugin
description: Ship a sandboxed plugin in any language, loaded at runtime with extism
---

WASM plugins let the community extend meili-ingest **without forking or
recompiling the worker**. The worker loads `.wasm` files at startup through
[extism](https://extism.org) and exposes them under the name in their manifest.

Good fit: lightweight transforms — custom parsers for niche formats, field
mapping, language detection, redaction. Not a fit: GPU work or huge native
dependencies — use a [gRPC plugin](/plugins/authoring-grpc).

## Contract

A module exports two functions. Both take and return JSON strings through the
extism plugin-input / plugin-output buffers.

| Export | Input | Output |
|---|---|---|
| `manifest` | — | `PluginManifest` JSON (`kind` is set to `wasm` by the host) |
| `execute` | `{ "input": PluginInput, "config": object, "job_id": uuid, "step_id": string, "attempt": number }` | `{ "ok": PluginOutput }` or `{ "error": { "message": string, "retryable": bool } }` |

`input` always comes first in the envelope. `job_id`, `step_id` and `attempt`
(1-based) name the step being run; a guest may ignore them. Older workers do
not send them, so read them as optional. A reply without `retryable`, a reply
that is not this JSON, an extism error and a trap all fail the step without a
retry.

With the Rust SDK, `ctx.job_id()`, `ctx.step_id()` and `ctx.attempt()` return
these values. `ctx.record_usage(..)` is discarded: the host does not take billable
usage from external plugins. `ctx.previous_progress()` is always `None`,
cancellation is never observed and `ctx.ai_target()` is never set.

`PluginInput` / `PluginOutput` use the tagged JSON shape from the SDK:

```json
{ "type": "documents", "value": [ { "id": "a", "content": "..." } ] }
{ "type": "bytes", "value": { "data": "<base64>", "mime": "application/pdf", "filename": "a.pdf" } }
```

The host resolves `Ref` inputs before calling you and spills large outputs
after, so the module only ever sees `bytes`, `documents`, `many` or `empty`.

Fetched bytes (a URL, an object ref, a scheduled source) also carry an `origin`
string. Generating ids from it keeps two fetched files of the same name apart:
the Rust SDK's `Blob::id_stem` does it the way the built-in plugins do.
Bytes fetched over HTTP whose `Content-Type` declares a `charset` carry it as
`charset` (lower-cased, for example `"windows-1252"`), while `mime` stays the
bare type. It is what the server declared, and the bytes are not decoded;
uploads have none.

Heartbeats: the host heartbeats on your behalf while the call runs. Keep
single calls under the step's `timeout_secs`; for big inputs prefer
`fan_out: "$.documents"` in the pipeline so each call handles one document.

## Editor hints

A client that renders a step's form from your `config_schema` (such as the Meilisearch
Lab console) shows a `string` property as a one-line input unless you add `"x-widget"`:

```json
"prompt": { "type": "string", "x-widget": "textarea" }
```

| Value | Renders as |
|---|---|
| `"textarea"` | multi-line text |
| `"code"` | multi-line monospace text |

Unknown values are ignored.

## Rust example (`extism-pdk`)

```toml
[package]
name = "meili-ingest-plugin-uppercase"
edition = "2024"

[lib]
crate-type = ["cdylib"]

[dependencies]
extism-pdk = "1"
meili-ingest-plugin-sdk = { version = "0.1", features = ["wasm"] }  # no tokio runtime inside the guest
serde_json = "1"
```

```rust
use extism_pdk::{plugin_fn, FnResult};
use meili_ingest_plugin_sdk::prelude::*;
use meili_ingest_plugin_sdk::wasm::{manifest_json, run_plugin};

struct Uppercase;

#[async_trait]
impl Plugin for Uppercase {
    fn manifest(&self) -> PluginManifest {
        PluginManifest::new("uppercase", "0.1.0")
            .description("Upper-cases document content")
            .accepts([InputKind::Documents, InputKind::Many])
            .produces(OutputKind::Documents)
    }

    async fn execute(
        &self,
        _ctx: &ActivityContext,
        input: PluginInput,
        _config: serde_json::Value,
    ) -> Result<PluginOutput, PluginError> {
        let docs = input.into_documents()?;
        let out = docs.into_iter().map(|mut d| { d.content = d.content.to_uppercase(); d }).collect();
        Ok(PluginOutput::Documents(out))
    }
}

#[plugin_fn]
pub fn manifest() -> FnResult<Vec<u8>> {
    Ok(manifest_json(&Uppercase))
}

// Decodes the envelope, runs `execute` and encodes the `{"ok"|"error"}` reply.
#[plugin_fn]
pub fn execute(input: Vec<u8>) -> FnResult<Vec<u8>> {
    Ok(run_plugin(&Uppercase, &input))
}
```

```bash
rustup target add wasm32-wasip1
cargo build --release --target wasm32-wasip1
# → target/wasm32-wasip1/release/meili_ingest_plugin_uppercase.wasm
```

Any language with an extism PDK (Go, JS/TS, Python, C, Zig, .NET, …) works the
same way: export `manifest` and `execute`, exchange JSON.

## Deploy

Mount the file into the worker pods of the pool that should run it and list it
in `EXTERNAL_PLUGINS`:

```yaml
env:
  - name: EXTERNAL_PLUGINS
    value: "wasm:/plugins/uppercase.wasm"
volumeMounts:
  - name: plugins
    mountPath: /plugins
    readOnly: true
```

Several entries are comma-separated and may mix kinds:
`wasm:/plugins/a.wasm,wasm:/plugins/b.wasm,grpc:http://ocr:50051`.

At boot the worker calls `manifest`, registers the plugin under that name and
publishes it to the control plane, so `GET /plugins` lists it with
`"kind": "wasm"` and pipelines can reference it immediately:

```yaml
steps:
  - id: extract
    plugin: pdf_extractor
  - id: shout
    plugin: uppercase
  - id: index
    plugin: meili_indexer
```

## Limits and sandboxing

- No network or filesystem unless you grant it through extism's manifest
  (`allowed_hosts`, `allowed_paths`) — the host runs modules with none by default.
- Memory is bounded by the wasm linear memory (4 GiB) unless the operator sets
  `WASM_PLUGIN_MAX_MEMORY_MB` on the worker. The cap covers the module's own
  memory plus the buffers holding its input and output, so set it well above
  the largest input the plugin receives. A call that needs more fails the step
  without a retry. Keep per-call inputs small (fan out per document).
- One instance of the module runs one call at a time; other steps using the
  plugin wait for it.
- A call is interrupted when its activity is cancelled (the job is cancelled,
  or Temporal reports the step timed out) or the worker stops waiting for it,
  and the module starts the next call from a fresh instance,
  so keep no state between calls. `WASM_PLUGIN_TIMEOUT_SECS` on the worker adds
  a ceiling for every call whatever the step allows; a call that reaches it
  fails the step without a retry. The interruption stops the module's code: a
  module blocked inside a host or WASI call is stopped once that call returns.
- The module runs on the worker's task queue; the name → queue table only
  knows the built-in names, so a WASM plugin runs wherever it is declared.
