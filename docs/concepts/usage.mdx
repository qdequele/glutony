title: "Usage & metering"
description: "Per-tenant usage data: what is recorded, how it reaches Tinybird, and which table to bill from."
---

Every job records what it consumed, per tenant, so you can bill for it and chart it.
The data lands in [Tinybird](https://www.tinybird.co) (managed ClickHouse) and is
written by the worker, never by the gateway. Tinybird holds the analytics. Behind the
Meilisearch Lab, the bill is a separate stream of events, described in
[Analytics and billing](#analytics-and-billing).

## What is recorded

One row per pipeline step, plus one row per job.

| Group | Fields |
|---|---|
| Identity | `job_id`, `workflow_id`, `project_id`, `region`, `pipeline_uid`, `index_name` |
| Shape | `kind` (`job` / `step`), `step_id`, `plugin`, `task_queue`, `branches` |
| Outcome | `status`, `error_kind`, `error`, `duration_ms` |
| Volume | `input_bytes`, `input_mime`, `documents_out` |
| Cost | `llm_input_tokens`, `llm_output_tokens`, `llm_requests`, `audio_seconds`, `pages`, `images`, `external_requests` |

Volume is observed by the worker. Cost units come from the plugins themselves, because
only the plugin knows what it spent on an external service: the enricher reports the
token counts the provider returned, the transcriber reports the audio seconds it was
billed for, the extractors report pages. Plugins report through
`ActivityContext::record_usage`, and the accumulator is shared across clones so a
plugin fanning out concurrently is not undercounted.

The Meilisearch API key never appears in an event. Only the tenant and `region` do.
The tenant id is stored in the Tinybird column `project_id`: renaming a Tinybird column
means a new data source and a backfill, so the column and the `tenant_usage` pipe
parameter keep their names.

## How it gets there

Reporting is a Temporal activity, not a fire-and-forget HTTP call. The workflow invokes
it on every terminal path, so a failed or cancelled job is metered too. It consumed
tokens and CPU, and that has to be billed.

<Note>
The reporting activity is deliberately detached from the workflow's cancellation
token. Activities inherit workflow cancellation, so without that a cancelled job would
be killed before it could report anything.
</Note>

Temporal retries the activity until it succeeds, which makes delivery at-least-once and
survives a worker crash. There is no attempt limit: the activity retries with a
5-minute maximum interval for up to 7 days, in every deployment. During an outage of
Tinybird or the control plane a workflow can therefore stay open that long, but the
job's own status is written first, so a slow usage report never holds back a job's
status. If the window runs out the job's own result is unchanged: losing a usage row
must never turn a successful ingest into a failure.

At-least-once is safe here because every row carries a deterministic `event_id`
(`{job_id}:{step_id}:{attempt}`, or `{job_id}:job`), and the data source is a
`ReplacingMergeTree`. A redelivery replaces the stored row instead of double-counting
it. Timestamps are deterministic too: every row of a job is stamped with the job's
finish time rather than "now", because `ReplacingMergeTree` deduplicates on the whole
sorting key.

## Which table to bill from

<Note>
`documents_out` on a step row counts a document once per stage, so a pipeline that
extracts then chunks then indexes reports it three times. That measures work done,
not corpus size. The rollups expose `documents_indexed` for the number that actually
reached Meilisearch, taken from the job row's final-step count — that is the figure
to bill on.
</Note>

| Table | Freshness | Deduplicated | Retention | Use for |
|---|---|---|---|---|
| `meili_ingest_usage` | real time | with `FINAL` | 180 days | drill-down, audits |
| `usage_daily` | real time | **no** | 180 days | dashboards, live estimates |
| `usage_daily_billing` | hourly | yes | indefinite | **invoices** |

A materialized view is a trigger on `INSERT` and never sees deduplication, so
`usage_daily` can over-count a redelivered event. `usage_daily_billing` is a scheduled
copy that re-reads the raw table with `FINAL`, trading an hour of freshness for
correctness. The `tenant_usage` endpoint reads it.

`usage_daily` keeps 180 days, like the raw table, because a deployment that changes
its materialized pipe rebuilds it from the raw rows. `usage_daily_billing` keeps every
day: it is the invoice record and no deployment recomputes it.

```bash
curl "https://api.tinybird.co/v0/pipes/tenant_usage.json?\
project_id=acme&date_from=2026-09-01&date_to=2026-09-30&token=$READ_TOKEN"
```

## Analytics and billing

Two streams leave the worker, and they have different jobs.

- **Tinybird rows are analytics.** They feed the dashboard and `GET /usage`. They
  are per step, they carry no price, and they are on for any deployment that sets
  `TINYBIRD_TOKEN`.
- **Lab events are the bill.** Behind the [Meilisearch Lab](/deployment/meilisearch-lab),
  each job run for a Lab account also produces one `usage.recorded` event with the
  same units plus `cost_micro_usd`. The Lab converts it to credits.

`cost_micro_usd` is what glutony paid providers for the job. It comes from the
provider cost table, `config/provider-costs.toml` (or the file named by
`PROVIDER_COSTS_FILE`), keyed by plugin and model. A call the table cannot price
costs 0 and sets `cost_complete: false` on the event, so the Lab sees the gap
instead of silently under-billing. Calls glutony does not pay for, such as a local
gRPC plugin, cost 0 and stay complete. The bundled prices are placeholders: set
yours before billing. A missing or invalid `PROVIDER_COSTS_FILE` stops the worker at
boot; if it ever fails to load later, calls are flagged unpriced instead of being
priced at the bundled rates.

The Lab event is written first, then Tinybird. A Tinybird failure cannot keep a bill
from being recorded, and a retry re-inserts the same event id harmlessly.

## Configuration

Set these on the workers. Without `TINYBIRD_TOKEN` usage reporting is simply off: the
worker logs that once at startup and the reporting step becomes a no-op, so self-hosted
deployments need no analytics account.

| Variable | Default | Description |
|---|---|---|
| `TINYBIRD_TOKEN` | — | Append token for the usage data source (`glutony_worker_append`, minted by every Tinybird deployment). Absent disables reporting. |
| `TINYBIRD_BASE_URL` | `https://api.tinybird.co` | Region-specific, e.g. `https://api.eu-central-1.aws.tinybird.co`. |
| `TINYBIRD_DATASOURCE` | `meili_ingest_usage` | Target data source name. |

Deploy the schema and pipes with the Tinybird Forward CLI from the `tinybird/` directory
(`tb --local deploy` against Tinybird Local, `tb --cloud deploy` against a workspace).
The deployment also mints the gateway's read token, `glutony_gateway_read`
(`TINYBIRD_READ_TOKEN`); see `tinybird/README.md`.

## Usage data is not monitoring

These two answer different questions and must stay separate. Prometheus answers "is the
system healthy" and its labels must stay low-cardinality, so the tenant id must never
become one. Per-tenant usage is inherently high-cardinality and belongs in a columnar
store.
